# Workspace Rules for SM64 Decomp & Level Viewer

- **Global Header Placement**: When adding dynamic configuration headers (such as `chaos_config.h`) that are shared across various modules (e.g. `src/game/`, `src/menu/`, `src/audio/`), write the file into the master `include/` directory. This allows universal `#include "chaos_config.h"` imports via the Makefile's `-Iinclude` flag.
- **SM64 Trig Macros**: When using `sins` or `coss` functions, always include `"engine/math_util.h"`. Since they are lookup macros rather than function symbols, neglecting the header causes implicit declaration warnings and linker failures.
- **Save File Macro Preservation**: When parsing level objects, macros, and special objects, store macro parameters verbatim using the `RawParams` string property. This prevents macro replacement expressions (like `BPARAM2(...)`) from being truncated to zero, avoiding in-game camera bugs when saving levels.
- **WSL Decomp Repository Path**: The active SM64 decomp repository inside the Linux build subsystem is located at the Windows UNC path `\\wsl.localhost\Ubuntu-20.04\root\sm64`. Use this path when analyzing build scripts, checking output artifacts, or mapping Windows file paths to WSL command execution.
- **Target GitHub Repository Syncing**: The active development workspace is a static download directory and is not a Git repository. Always synchronize/propagate any modified or new files to the primary GitHub repository path `C:\Users\Intel\OneDrive\Documents\GitHub\Randm64` after editing, while excluding `.vs`, `.agents`, `bin`, and `obj` folders.
- **No Git Commands in Workspace**: Do not run Git commands (such as `git status`, `git diff`) in this downloads workspace directory.
- **IDO Compatibility & Code Injection**: When generating, injecting, or writing custom C code (for chaos modes or custom C patches on the patching window), respect the limitations of the SGI IDO compiler and the original SM64 coding style. Ensure all variables are declared at the beginning of their scope (before any executable statements), strictly adhere to original brace styling and placement conventions, and avoid C99 features or unsupported constructs to prevent compilation and syntax errors.

## SM64 Music Playback Accuracy

Apply these rules when changing the music editor, M64 parsing, sample decoding, sound-bank resolution, or audio mixing. Preserve the corrected playback behavior; changes to these rules should be supported by the target game's audio source and regression checks.

- **Use game data as the reference**: Consult the target decomp's `src/audio/seqplayer.c`, `playback.c`, `effects.c`, `synthesis.c`, `data.c`, and `tools/assemble_sound.py` when changing audio semantics. Resolve sequence banks from `sound/sequences.json` and instruments from their bank JSON. Prefer the actual SM64 samples over General MIDI; preserve the explicit MIDI preview option and investigate unexpected fallback.
- **Sample loops**: One-shot samples must finish at their PCM end. Sustained samples must repeat only their declared loop region, preserving the attack outside it. Read AIFF `MARK`/`INST` markers and Nintendo `APPL/stoc/VADPCMLOOPS` metadata; validate frame bounds and preserve loop count/direction. Do not loop entire samples unconditionally or guess looping behavior from instrument filenames.
- **Percussion lookup and pitch**: Standard banks store drums in `instruments.percussion`. Instrument ID 127 selects percussion, and the sequence semitone indexes the drum array directly; do not subtract the MIDI drum offset of 21. Apply each drum's own tuning, pan, envelope, and release rate. Drum tuning already determines playback frequency: do not apply melodic pitch transposition a second time.
- **Regional sound-bank conditions**: Resolve nested `ifdef/then/else` JSON using the sequence folder's region (`us`, `jp`, `eu`, `sh`, or `cn`), matching `assemble_sound.py`'s any-matching-define rule. Cache resolved banks per region. Conditional sound entries are not missing samples: the US puzzle-solved and Piranha Plant sequences use `piranha_music_box/00_music_box_C5.aiff`. Retain tests proving these resolve to the real music box instead of MIDI fallback, and that SH/CN select their own branch.
- **Melodic instruments and dynamics**: Preserve low/normal/high sample ranges and per-sound tuning. The melodic frequency reference is `2^((pitch - 39) / 12)`; the game's upper frequency-table entries have special behavior. Preserve squared velocity response, cosine/sine pan gains, sound-bank ADSR envelopes, and instrument-specific release rates rather than replacing them with linear velocity, filename heuristics, or a single generic fade. Keep fixed mixing headroom to avoid clipping and changes in loudness as polyphony changes.
- **Live volume preview**: Volume-slider edits must affect active and future notes in both sample and MIDI preview. Keep channel gain separate from velocity/pan, smooth live sample gain changes, and support muting/unmuting without killing voices or dividing by zero. Retain edits across stop/seek/loop, clear preview overrides when loading another sequence, and preserve scripted note volumes until the user explicitly changes that channel's slider.
- **Note timing and voice identity**: M64 gate specifies the silent fraction at the end of a note delay: `silentTicks = delay * gate / 256` using integer arithmetic, and audible duration is `max(1, delay - silentTicks)`. A zero gate means full duration; `note1` resets gate to zero. Keep note starts in caller order, preload samples before starting the playback clock, and schedule sample releases in audio frames. Do not reintroduce per-note `Task.Run` races or let a note-off cut a different layer's same-pitch voice.
- **Reverb and transport**: Preserve per-note/channel reverb sends, decaying feedback, and reverb clearing on transport reset. The current room preview uses the US default session's `0xC00`-sample ring at 32 kHz and feedback `0x2FFF / 0x8000`, scaled to the output rate. These are a default preset, not universal settings for every room or region. Do not substitute an arbitrary echo or describe this preview as emulating the RSP's fixed-point processing and resampling filter.
- **Tempo changes**: Preserve `seq_settempo` and signed US/EU `seq_addtempo` events at their sequence ticks. Advance the playhead and compute sample release durations through the tempo map, including notes and timer updates that cross tempo boundaries. Do not apply the last parsed BPM to the entire song. The US title-screen M64 includes a slower Game Over section with multiple tempo changes; retain its regression coverage alongside constant-tempo tracks, seeks/loops, and sequence reloads.
- **Safe M64 saving**: Preserve unchanged sequence bytes and scripted controls. Added overlapping notes need independent layers (at most four per channel); never silently discard them. Encode pitches above 63 with layer transposition instead of `pitch & 0x3f`, and write explicit delays after redistributing compact notes. Preserve original layer scripts when adding notes into free slots; reject edits whose control flow/effects cannot be preserved. Build a complete staged file, validate limits, retain the first backup, detect external edits, and replace the target only after successful encoding. Never restore stale `.bak` content as the basis of a subsequent save, or show success after a failed save. Retain round-trip tests for stacks, high/low pitches, repeated/no-op saves, and failures that leave the target unchanged.
- **Validation baseline**: The user reported that Bob-omb Battlefield and at least four SM64 tracks sounded similar to the original after these fixes. Preserve this listening baseline, but do not treat it as proof of bit-perfect N64 playback. For audio changes, run the offline regression harness below and a Release build. When listening validation is available, compare several tracks against the game, including percussion, sustained instruments, and reverb tails.

Run from the project root (the harness does not open an audio device):

```powershell

dotnet run --project .\Tests\AudioPlayback\AudioPlayback.csproj -c Release -- '\\wsl.localhost\Ubuntu-20.04\root\sm64'
dotnet build .\Randm64.csproj -c Release
```

The second command additionally checks the real WSL sound bank and extracted AIFF samples; use the active decomp path if it changes. Keep regression coverage for one-shot termination, loop boundaries, drum lookup/tuning, independent layers, gate semantics, sample-clock releases, envelopes, and reverb delay/decay/reset when changing those paths.
